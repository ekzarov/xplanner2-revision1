# Repository Artifact Map

**Agent roles and skills:** [analysis/agent-roles.md](analysis/agent-roles.md)
maps each stage to PM, BA, UX, Architect, Developer or QA. The six
`.agents/skills/migration-*/SKILL.md` files are copied reusable instructions,
explicitly read by the assigned session. `CLAUDE.md` and `AGENTS.md` route to
MIGRATION.md; neither defines a competing process. The process maintainer owns
these files; they are not project evidence. Generic "stage agent" authorship
below resolves through this role map for new/reopened work, not retroactively.

All authored Markdown families use the [human-readable artifact contract](analysis/artifact-reading-contract.md):
purpose and authorship, a scoped color summary, anchored contents, and structured
results with explicit remaining work. The [template profiles](analysis/artifact-reading-profiles.json)
cover Bootstrap and Stages 1-19; their summaries never replace evidence or approval.

**Reading technical statuses.** Machine labels remain unchanged. Their plain-language meanings and approval boundaries are explained beside editable records and in the companion reference for strict formats and historical evidence. [Status meanings](analysis/artifact-status-meanings.md).

This is the authoritative catalog of every governed artifact in the starter
and in a repository initialized from it. It explains what each file is, why it
exists, when it is used, who updates it, how it comes into existence, and what
depends on it. [`MIGRATION.md`](MIGRATION.md) owns session routing and immediate
stop/transition rules; [`analysis/migration_methodology.md`](analysis/migration_methodology.md)
owns the detailed procedure for the stage selected by status. This catalog only
maps the artifact system and never overrides either document.

**Who writes project artifacts:** the actor named by the active stage creates or
updates its repository files by following that stage's procedure in
[`analysis/migration_methodology.md`](analysis/migration_methodology.md). The
linked template defines structure; the stage's approved input artifacts define
content. An owner point means the owner supplies an explicit decision or
signature. Unless a record explicitly requires owner authorship, the stage agent
writes the file and records the owner's decision without inventing it.

For exact filenames, see [Artifact Naming](analysis/artifact-naming.md): every
template maps to a project output with the same filename stem. Historical
XPlanner examples retain their existing filenames.

## Lifecycle Legend

| Code | Lifecycle | Meaning |
|---|---|---|
| `SRC` | SOURCE-ONLY | Exists only in the starter source repository; `init-migration.ps1` never copies it into a project. |
| `CPY` | COPIED BY INITIALIZER | Copied verbatim from the starter payload into every initialized project. |
| `GEN` | GENERATED BY INITIALIZER | Rendered or instantiated by `init-migration.ps1` with project identity; does not exist in the starter under its final name. |
| `MIG` | CREATED DURING MIGRATION | Created by agents or the owner while executing the governed migration process, from the templates and contracts in this catalog. |
| `PRJ` | PROJECT-SPECIFIC | The project's own legacy snapshot and target implementation source; never exists in the starter and is not enumerated here. |

## Reading Path For A Cold Agent

For the compact relationship view and the proposed daily working path, open
[`analysis/artifact-relationship-graph.md`](analysis/artifact-relationship-graph.md).
This catalogue remains the exhaustive reference.

An agent with no prior context reads, in order:

1. [`MIGRATION.md`](MIGRATION.md) — session router: what is permitted now, what to read next, and where to stop.
2. [`.specify/memory/constitution.md`](.specify/memory/constitution.md) — highest project authority after the entry point; ratified per project.
3. [`analysis/migration_status.yaml`](./analysis/migration_status.yaml) (initialized projects) — the single current-stage checkpoint; absent or invalid means bootstrap mode.
4. [`analysis/migration_methodology.md`](analysis/migration_methodology.md) — detailed procedure for the selected stage: inputs, work, actors, outputs, gate, and return path.
5. [`config/project.yaml`](./config/project.yaml) (initialized projects) — exact paths, target platforms, and the operational command contract.
6. [`config/environments.yaml`](./config/environments.yaml) — the remote environment contract, before any remote operation.
7. [`analysis/tools/README.md`](analysis/tools/README.md) — canonical audit commands and waiver semantics.
8. This catalog — to locate the artifacts of the active stage.
9. The active stage's own instructions and artifacts (see the grouped table below).

```text
entry                MIGRATION.md, AGENTS.md, README.md
  └─> authority      .specify/memory/constitution.md  +  analysis/migration_status.yaml
        └─> process  analysis/migration_methodology.md (+ .html view)
            config   config/project.yaml, config/environments.yaml (+ schemas)
              └─> evidence & design
                    analysis/legacy_reconnaissance.md, analysis/legacy_user_flows.xlsx,
                    analysis/prototyping/*, analysis/architecture/*, analysis/inventories/*
                    └─> SDD  specs/NNN-*/, specs/traceability.md, .specify/templates/*
                          └─> build & delivery
                                Stage 17 PRs, analysis/stages/stage-18/*, audit:target/:delivery
                                └─> acceptance
                                      analysis/reviews/stage-19-pass-NNN.md, audit:stage19,
                                      owner acceptance in analysis/migration_status.yaml
                                      audit:all validates final complete only
```

Every layer is gated by the deterministic audits in [`analysis/tools/`](./analysis/tools) and by
the owner decisions recorded in [`analysis/migration_status.yaml`](./analysis/migration_status.yaml).

## Practical Use

Read every artifact through three questions:

1. **When is it used?** The stage column says when the artifact is created,
   read, updated, reviewed, or pinned.
2. **How is it used?** The consumer and downstream columns name the action it
   supports, such as selecting the active stage, constraining an SDD, running a
   command, checking a hash, or proving a live result.
3. **What is a concrete use?** The examples below show the artifact chain in
   practice. They explain usage only and never substitute for project evidence.

| Phase | When and how the artifacts are used | Example use |
|---|---|---|
| Bootstrap and control | `AGENTS.md` and `MIGRATION.md` route every session; the constitution limits authority; status selects the active stage; project and environment contracts supply exact commands and destinations. | At Stage 17 the agent runs the test command from [`config/project.yaml`](./config/project.yaml); before Stage 18 it resolves the approved host and endpoint from [`config/environments.yaml`](./config/environments.yaml). |
| Requirements | Stage 1 fills reconnaissance and the parity map; Stages 2–4 challenge the evidence, compare it with the running legacy system, and record business decisions. | A failed-login row links source evidence to a keep decision; a Stage 2 report returns it to Stage 1 when the reviewer discovers a missing password-expiry path. |
| Prototyping | Stage 5 records the owner’s design baseline; Stage 6 normalizes rows and creates wireframes plus their manifest; Stages 7–8 review and pin the exact set. | A task-delete row maps to a confirmation state, while a nightly batch job is marked non-visual with a reason. The owner approves the exact export hash. |
| Architecture and knowledge | Stage 9 turns facts and client answers into NFRs and decisions; Stages 10–12 review and approve the package; Stages 13–14 produce and verify source-linked knowledge. | The client confirms 50 concurrent users; the workbook records the capacity NFR, an ADR explains the deployment choice, and an OKF concept cites that approved source. |
| Design | Stage 15 creates the slice spec, plan, tasks, traceability and target inventory; Stage 16 independently checks the complete chain and exposes assumptions to the owner. | A time-entry row links to its decimal-duration requirement, implementation task, test, and `/tasks/{id}/time` target route. |
| Coding | Stage 17 changes code only for approved tasks and packages tests, migrations and synchronized evidence in one pinned candidate. | A report service, its unit tests and schema migration enter one PR; the owner merges the SHA that passed the declared checks. |
| Delivery and acceptance | Stages 18-19 bind the deployed SHA to delivery, browser, rollback, live-revision, independent review and owner-acceptance evidence. | The browser signs in as a member, records 2.5 hours, verifies the daily total and signs out; the delivery record pins that run to the deployed revision. |

## Starter Source Vs Initialized Project

Only the starter source repository contains:

- [`.migration-starter-source`](.migration-starter-source) — the pinned repository-identity marker; copying it cannot bypass project audits because CI also checks the actual repository identity;
- [`tests/init-migration.Tests.ps1`](tests/init-migration.Tests.ps1) — the initializer self-test suite;
- [`analysis/reviews/starter-governance-hardening-review.md`](analysis/reviews/starter-governance-hardening-review.md) — starter-repository governance evidence.

Everything else in the grouped table marked `CPY` arrives in an initialized
project byte-identical to the starter; `GEN` artifacts are rendered with the
project's identity; `MIG` artifacts start absent and accumulate as evidence
while the numbered stages and delivery loops execute.
