# Human-Readable Artifact Contract

**What has been established, what is still wrong or unknown, and what happens next?**

This is an authoring rule, not a new approval authority. The active-stage agent
creates each record from its named template and follows the
[result boundaries](artifact-result-boundaries.md) and
[status meanings](artifact-status-meanings.md). The process-maintenance agent
maintains this contract and the [template profiles](artifact-reading-profiles.json).

## First Screen

Every new or reopened Markdown artifact has this reading order:

1. A literal title and a short question explaining the artifact's purpose.
2. Collapsed reusable guidance: purpose, author, decision maker, instructions and examples.
3. Collapsed template/status notes, separate from actual project evidence.
4. One visible color-coded summary: the recorded outcome, the most important
   unresolved item or reconciled statistic, and a link to the next action.
5. A Contents control with working links to the record's sections.
6. Detailed observations, comparisons, decisions, corrections and evidence.

Use short paragraphs and lists for distinct obligations. Use tables for repeated
items with comparable fields, not for long narrative paragraphs. Keep original
finding IDs, exact machine fields, attribution and historical boundaries.

## Color Is Not Authority

Use GitHub-compatible alerts, not inline CSS, an image badge or a gradient that
disappears in repository Markdown. Every color also has a plain-language title.
The supported syntax is described in the
[GitHub Markdown reference](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts).

| Alert | Meaning in a record | Must not imply |
|---|---|---|
| CAUTION, red | Recorded failure, blocking findings or an invalid required review | A newly discovered defect if merely restating an old report |
| WARNING, amber | Draft, pending decision, incomplete evidence or a bounded conditional result | Permission to ignore a mandatory blocker |
| TIP, green | A positive result is actually recorded for the explicit scope and exact version | Global completion, owner approval or fresh verification beyond that result |
| NOTE, neutral | A reference/source document or no single overall verdict | An invented success or failure |

An unfilled template starts amber: **Template: not yet assessed**. Placeholders
and empty tables are not zero findings. A source document, an authored SDD, a
deployed release and independent acceptance are different states.

The agent writes a concrete summary from the detailed result, not from the
desired outcome. Example: "Two checks failed and one could not run; the reviewer
returns the affected scope to Stage 6." Counts name their unit and reconcile to
the detailed ledger. Do not add row, screen, test and finding counts together.

For partial approval, lead with the overall limit and name the approved subset.
For historical evidence, say "recorded result", retain its date/revision and
never imply the formatting operation reran the review. If the verdict is
ambiguous or contradictory, use a neutral/amber summary and explain that limit.

## Writing And Updating

The author uses the exact family template. After completing its body, the agent
replaces the template summary with two or three human-readable sentences and,
where useful, a short reconciled statistic. Link the result and outstanding-work
sections. The summary is a reading aid; the canonical verdict and evidence remain
in their original fields below. Changes to either require keeping them consistent.

The template formatter is `node analysis/tools/artifact-reading.js --write-templates`.
It changes templates only; it must not be used to turn existing evidence green.
The read-only structural check is `npm --prefix analysis/tools run audit:readability`.
For a newly authored file, use
`node analysis/tools/artifact-reading.js --file <repository-relative-file.md>`.
The check verifies structure and links, not the truth of the verdict. Human
review and the stage's existing gates retain that responsibility.

The author updates Contents after changing headings, preserves existing
section anchors, and uses the explicit reading anchors generated by the tool.
A copied template must retain its summary/Contents structure; generation never
constitutes approval. Template synchronizers preserve the reading layout.

## Existing Evidence

Normal process work does not rewrite immutable reports or silently repin an
approved set. A correction gets the record/version required by the process.
A specifically owner-authorized editorial migration may update old Markdown and
dependent file hashes, but records its authorization, original source revision,
old/new hashes, unchanged substantive results and checks deliberately not rerun.
Such maintenance never creates a clean pass or changes the current stage.

The one-off XPlanner formatting authorization is project-specific. It is not a
new general-purpose waiver, a change to the Starter gate rules or permission for
future agents to bypass verification.

## Coverage Of All 20 Checkpoints

| Checkpoint | Markdown record / reading surface | Boundary to show first |
|---|---|---|
| 0 Bootstrap | Bootstrap gate report and constitution | Executed setup checks versus separate owner ratification/authorization |
| 1 Reconnaissance | Legacy reconnaissance | Discovered facts, evidence, gaps and source coverage |
| 2 Control reconnaissance | Independent stage review | Blind inventory, reconciliation, findings and verdict |
| 3 Legacy walkthrough | Walkthrough record | Live, simulated, blocked and unverified scope |
| 4 Requirements revision | Requirements revision record | Owner decisions versus proposals and unapplied changes |
| 5 Application form/style | Decision record | Selected baseline versus pending choices |
| 6 Wireframes | Prototyping companion guide; JSON normalization/manifest and exports remain structured files | Planned representation versus produced coverage; no extra review report invented |
| 7 Wireframe control | Independent review; conditional cosmetic backlog | Findings versus eligible bounded cosmetic deferrals |
| 8 Owner prototype review | Approval record | Exact approved exports versus remarks and unreviewed scope |
| 9 Architecture | NFR owner review, architecture, sections and ADRs | Approved decisions versus proposals, delivery limits and missing inputs |
| 10 Architecture control | Independent review; applicable waiver as input | Scope checked, findings, permitted exception and remaining obligations |
| 11 Owner architecture review | Architecture owner verdict | Owner decision and original remarks |
| 12 Remark closure | Separate immutable architecture-closure-NNN.md | Criterion, observation, evidence, reconciled counts and exact return; owner verdict remains read-only |
| 13 Knowledge synthesis | Knowledge record, index and concepts | Produced concepts versus missing coverage and source approval |
| 14 Knowledge control | Independent review | Source/concept correctness and exact review boundary |
| 15 Design | SDD record, spec, plan, tasks and traceability | Authored coverage, assumptions and design gaps |
| 16 Design control | Independent review and owner decision | Verified design versus permission to implement |
| 17 Implementation | Tasks and traceability; linked execution/review evidence | Implementation finished versus delivery/verification still open |
| 18 Delivery and live reconciliation | Delivery record with Live Reconciliation | Exact release, actual behavior and executed checks versus approved expectations and unchecked scope |
| 19 Acceptance | Independent acceptance; optional owner walkthrough or decline | Independent result versus separate final owner acceptance |

The 28 template families cover these checkpoints without adding duplicate
artifacts. Structured JSON, YAML, spreadsheets and exported wireframes keep their
schemas; their Markdown companion guides carry the human explanation.
