# Starter Process Canvas

This static Three.js view explains the reusable migration process independently
of any one migrated product. It shows Bootstrap and Stages 1-19, their actors,
owner gates, independent controls, automated audits, primary artifacts, exit
criteria, and return paths.

For every selected stage, the canvas distinguishes artifacts consumed as
inputs, produced as outputs, and read then changed as updated artifacts. The
same role and stable artifact code appear on the 3D marker and in the details
panel.

Bootstrap creates [`analysis/migration_status.yaml`](../migration_status.yaml). The data generator then
adds it automatically to every Stage 1-19 as a standing input and updated
output, so individual stage definitions must not duplicate or omit this global
`U` artifact. `audit:views` enforces the invariant.

## Agent Checks

Frames describe required responsibilities, never completed work or a passed gate.
They distinguish independent review from verification by the responsible agent.
The [methodology](../migration_methodology.md) and
[agent orchestration](../agent_orchestration.md) remain authoritative.

| Stages | Frame and badge | Process meaning |
|---|---|---|
| 2, 7, 10, 14, 16, 19 | Solid cyan; AI REVIEW | Six standalone independent control stages, each with a fresh eligible reviewer and its own verdict. |
| 17 | Solid cyan; AI + AI REVIEW + HUMAN | Implementation includes a separate independent peer review before owner-authorized merge. It is not a seventh standalone control stage. |
| 3, 12, 18 | Dashed cyan; AI CHECK | The responsible agent verifies live legacy behavior (3), owner-remark closure (12), or delivered behavior and coverage (18). These activities do not replace independent controls. |
| Bootstrap, 1, 4, 5, 6, 8, 9, 11, 13, 15 | No agent-check frame | Preparation, authoring or owner decisions. Routine self-checks and scripted gates do not turn these into agent-review stages. Human decisions keep their HUMAN marker. |

In particular, Stage 12 does not require a fresh independent reviewer of its own.
Corrections still follow the classified return and repeat affected controls,
including Stage 10 architecture review and the owner's verdict. Stage 17's
reviewer is distinct from the implementation author. Neither visual convention
changes the `independent` flag or the governed review ledger.

`checkRole` is view metadata: `independent`, `peer`, `primary` or `none`.
The generator derives `independent` from the existing formal stage flag and
declares the other checking roles on their stage definitions. Regression tests
cover every checkpoint, so actor changes require an explicit mapping review.

## Files

Single-clicking a stage cube opens its description. Double-clicking flies the
camera to a fixed oblique close view, hides the description and retains the
selected stage's artifact connections. The cube becomes the orbit center;
world Y-up and the overview orientation are unchanged. Manual orbit/zoom/pan
interrupts the flight. Reduced-motion preferences use an immediate transition.

Pressing or clicking the canvas preserves phase-label positions. Manual orbit,
pan and zoom move the camera, not the phase-label anchors. Only an explicit
phase/cube focus or complete-process reset changes the label layout.

The browser regression test covers blank clicks, cube selection, double-click
focus, reset, orbit and zoom in EN/RU at desktop/mobile widths, including a
nonblank canvas-pixel check. Run `node tests/process-canvas.browser.cjs` with
Playwright available, or set `PLAYWRIGHT_MODULE` to an installed module path.
An optional URL argument checks the deployed canvas; `SCREENSHOT_DIR` saves
screenshots without adding generated images to the repository.

- [Process contract](../process-contract.md) is the English MD source for shared
  flow, responsibilities and closing evidence. Detailed procedures remain in
  the methodology and companion MD instructions.
- `build-data.js` supplies presentation explanations and examples subordinate
  to those MD rules; it imports stage flow instead of defining a second flow.
- `data.json` is generated by `node analysis/process-canvas/build-data.js`.
- [Stage gate contract](../stage-gates.json) supplies required checks and
  evidence conditions. Stage 19 acceptance and final completion are separate.
- [Record profiles](../record-contracts.json) supply EN/RU evidence boundaries
  for artifact cards and the matching Markdown, HTML and Draw.io descriptions.
- [Artifact naming](../artifact-naming.md) maps starter templates to new-project
  filenames. The generator reads that mapping for the card's output path;
  existing XPlanner examples keep their historical names.
- `sync-practical-guidance.js` projects the same practical explanations into
  `ARTIFACTS.md` and [`analysis/tools/README.md`](../tools/README.md); its `--check` mode catches
  drift between the 3D cards and the repository guides.
- `index.html`, `styles.css`, and `app.js` provide the interactive view.
- `vendor/` contains the locally served Three.js runtime used by the view.

After changing the governed methodology, the process-maintenance agent updates
the affected English MD contract and presentation explanations, then runs:

```text
node analysis/tools/process-contract.js --write
node analysis/process-canvas/build-data.js
node analysis/process-canvas/sync-practical-guidance.js
npm --prefix analysis/tools run sync:stage-gates
npm --prefix analysis/tools run audit:views
```

Russian is only a 3D translation. Run `node analysis/tools/translation-audit.js`
to detect missing or changed translations, including historical-example notes.
After actually reviewing every changed EN/RU pair, use its `--record-reviewed`
option and rerun the check. Never refresh this binding merely to obtain green:
it identifies reviewed wording, not a successful migration gate or owner approval.

For an existing project, synchronize its guidance with
`--target-root=<absolute-project-path>` and update its copied contracts and
matrix views too. Preserve project-specific code and historical evidence.
Check the canvas on desktop and mobile viewports. The canvas is
a human explanation of the canonical Markdown process; it does not replace
`MIGRATION.md`, the constitution, the methodology, or project status.
`MIGRATION.md` routes each agent session and enforces immediate stop rules;
`migration_methodology.md` explains how the stage selected by status is
performed and completed. Their separate artifact cards make this division
explicit.

The shared demonstration publishes this directory at `/starter-process/` and
keeps `/xplanner2/process/` as a compatibility redirect.

Public releases are uploaded to immutable directories under
`/opt/starter-process/releases/<revision>`. The deployment switches the
`/opt/starter-process/current` link only after the new release is complete.
